# Tax on Transactions — Design

## Approach

When a posting line carries a `tax_rate_id`, the create handler expands
the line set with an explicit **tax leg**: a normal posting to the tax
rate's `account_id`, on the **same side** (debit or credit) as the taxed
line, with amount `round(line_amount × rate, 2)`. The tax legs are part
of the postings passed to `PostingService`, so the existing balance
validation, period-close check, ledger lock, and DB trigger all apply to
them unchanged. A parallel `TaxLink` list tells the service which
posting each tax attaches to so it can write `posting_taxes`
(`posting_id`, `tax_rate_id`, `base_amount`, `tax_amount`).

## Decisions

- **Tax-exclusive entry.** The amount typed on a line is the *net*
  amount; tax is added on top. WHY: matches how people enter a purchase
  ("the item was 100, plus 10% VAT"). Alternative considered:
  tax-inclusive (typed amount includes tax) — rejected for v1 because it
  complicates the balancing editor and the balancer math.

- **Tax legs are explicit postings generated by the handler.** WHY: the
  service, the reversal flow, and the reports all treat tax legs as
  ordinary postings with zero special cases; the only new write is the
  `posting_taxes` linkage. Mitigation: the handler records the original
  line index in `TaxLink`, so the linkage is unambiguous even when tax
  legs are interleaved.

- **The balancing line cannot carry tax.** The tax selector is disabled
  on the row currently holding the balancing role. WHY: the balancer's
  amount is derived from the net of the other rows; giving it its own
  tax would make the balance circular. Mitigation: when a fixed row is
  promoted to balancer (or the balancer is promoted to fixed), the JS
  flips the disabled state, and clearing is automatic on promotion.

- **Simple entry mode is untouched (non-goal).** WHY: simple mode builds
  exactly two balanced lines of equal amount; adding tax would require a
  third leg and a definition of whether the amount is net or gross.
  Mitigation: the spec lists it as future work; advanced mode is the
  default entry mode.

- **No new tables; one small column.** `tax_rates` and `posting_taxes`
  already exist. Only `posting_taxes.base_amount` is added so the report
  can show net/tax/gross per rate. WHY: reuse of the existing schema
  keeps the migration minimal. Risk: existing rows have NULL base — low
  (no rows exist yet in practice). Mitigation: the report treats NULL as 0.

- **Reversal/correction carries tax legs as normal postings.** WHY: the
  reverse and edit flows clone postings; tax legs are ordinary postings
  so they are negated correctly. `posting_taxes` linkage is not copied
  to the *corrected* transaction — the original keeps its attribution.
  Mitigation: acceptable for v1; the tax report still shows the original
  transaction.

## Schema Change

Migration `0048_add_posting_tax_base.sql`:

```sql
ALTER TABLE posting_taxes ADD COLUMN IF NOT EXISTS base_amount NUMERIC(20,4);
```

(and a matching `.down.sql` that drops the column).

## Data Flow

1. `new.html` Advanced lines each render a tax `<select>` backed by the
   ledger's active rates.
2. `entry.js` recomputes the balancing line including tax on the same
   side as each taxed line; disables the tax select on the balancer.
3. The create handler parses `lines[N][tax_rate_id]`, validates the rate
   belongs to the ledger and is active, appends tax legs to the line
   set, records `TaxLink`s, and passes both to `PostingService`.
4. `PostingService::create_with_kind` inserts each posting (capturing
   `RETURNING id`), then writes one `posting_taxes` row per `TaxLink`.
5. The tax report groups `posting_taxes` by rate with base/tax/gross.

## Risks / Trade-offs

- A tax leg makes the transaction have `lines.len() > 2` even for a
  one-line expense — the balancer must be present, which the UI enforces.
  Mitigation: the editor always keeps one balancing row.
- Users may pick the same tax account as another line, tripping the
  "same account on both sides" guard. Mitigation: that guard runs on the
  user's lines before tax legs are appended, and the tax account is
  typically distinct.
